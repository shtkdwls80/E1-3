# MAC 필터 판정 콘솔 애플리케이션

n×n 패턴(0/1 등 숫자 행렬)을 **Cross(+)** 필터와 **X** 필터에 각각 MAC 연산(위치별 곱의 총합)한 뒤,
점수가 더 높은 쪽으로 패턴의 종류를 판정하는 콘솔 프로그램입니다.
외부 라이브러리 없이 **표준 라이브러리(`json`, `time`)만** 사용합니다.

---

## 1. 실행 방법

### 환경
- Python 3.8 이상 (표준 라이브러리만 사용, 별도 설치 불필요)

### 실행
```bash
python E1-3.py
```
(파일명을 `main.py`로 바꿨다면 `python main.py`)

### 모드 선택
실행하면 아래 메뉴가 나오며 `1` 또는 `2`를 입력합니다. 그 외 입력은 안내 후 다시 묻습니다.

```
1) 사용자 입력(3×3)
2) data.json 분석
```

| 모드 | 설명 |
|------|------|
| 1 | 필터 A(Cross), 필터 B(X), 패턴을 각각 3×3으로 직접 입력 → 점수/판정/연산 시간 출력 |
| 2 | `data.json`을 읽어 모든 케이스를 일괄 판정 → 케이스별 결과, 성능 분석표, 결과 요약 출력 |

### 모드 1 입력 방법
- 한 줄에 3개의 숫자를 **공백으로 구분**해 입력합니다. (예: `0 1 0`)
- 열 개수가 다르거나 숫자가 아닌 값이 있으면 오류 메시지 후 **해당 행렬을 처음부터 재입력**합니다.

### 모드 2 data.json 위치
- `E1-3.py`와 **같은 폴더**에 `data.json`을 둡니다. (현재 작업 디렉터리 기준 상대경로 `data.json`)
- 파일이 없거나 JSON 형식이 잘못된 경우 오류 메시지만 출력하고 프로그램은 중단 없이 종료됩니다.

### data.json 구조 (코드가 기대하는 형태)
```json
{
  "filters": {
    "size_5":  { "cross": [[...5x5...]], "x": [[...5x5...]] },
    "size_13": { "cross": [[...]],       "x": [[...]] }
  },
  "patterns": {
    "size_5_0": { "input": [[...5x5...]], "expected": "+" },
    "size_5_1": { "input": [[...5x5...]], "expected": "x" }
  }
}
```
- 패턴 키(`size_5_0`)의 숫자 `5`를 N으로 추출하고, `filters`의 `size_5` 필터를 사용합니다.

## 2. 구현 요약

### 2-1. 데이터 구조
- `Matrix` 클래스: `data`(2차원 리스트)와 `n`(크기)을 보관하고 `get / set / size`를 제공합니다.

### 2-2. 라벨 정규화 (`normalize_label`)
`expected` 값(`"+"`, `"x"`)과 필터 키(`"cross"`, `"x"`)가 서로 다른 표기를 쓰기 때문에,
비교 전에 모두 **내부 표준 라벨 `Cross` / `X` 두 가지**로 통일합니다.

| 입력(대소문자·공백 무시) | 표준 라벨 |
|---|---|
| `+`, `cross`, `십자가` | `Cross` |
| `x`, `엑스` | `X` |
| 그 외 / `None` | `None` (정규화 실패 → FAIL 처리) |

`str(raw).strip().lower()`를 거치므로 `" X "`, `"Cross"`, `"CROSS"` 같은 표기 차이도 흡수합니다.

### 2-3. MAC 연산 (`mac`)
- 이중 반복문(행 r, 열 c)으로 `pattern[r][c] * filter[r][c]`를 모두 더해 `float` 점수를 반환합니다.
- 패턴과 필터의 크기가 다르면 `ValueError`를 발생시키고, 모드 2에서는 **케이스 단위로 잡아서** 해당 케이스만 FAIL 처리합니다. (한 케이스의 오류가 전체 실행을 멈추지 않음)

### 2-4. 동점 처리 정책 (`decide`, epsilon)
- 부동소수점 오차 때문에 `==` 비교는 위험하므로 `EPSILON = 1e-9`를 사용합니다.
- `|score_cross - score_x| < 1e-9` 이면 **`UNDECIDED`**(판정 불가)로 처리합니다.
- 그렇지 않으면 점수가 큰 쪽(`Cross` 또는 `X`)을 반환합니다.
- `UNDECIDED`는 `expected`(Cross/X)와 절대 같을 수 없으므로 모드 2에서는 FAIL로 집계됩니다.

### 2-5. 모드 2 처리 흐름
1. `data.json` 로드 (실패 시 안내 후 종료)
2. 패턴별로 스키마 검증(`input`/`expected` 존재) → N 추출 → 필터(`size_N`) 선택 → 필터 라벨 정규화 → `expected` 정규화
3. Cross/X 두 필터로 MAC 연산 → `decide()`로 판정 → `expected`와 비교해 PASS/FAIL
4. 성능 분석표 출력 → 결과 요약(전체/통과/실패, 실패 사유 목록) 출력

### 2-6. 성능 측정 (`measure_mac`)
- `time.perf_counter()`로 **MAC 연산 구간만** 측정하고(입출력 제외), `REPEAT = 10`회 반복한 **평균(ms)** 을 구합니다.
- 크기 3, 5, 13, 25에 대해 측정하며, `data.json`에 해당 필터가 없으면 1로 채운 n×n 임시 행렬을 사용합니다.

### 3-2. FAIL 케이스 원인 분석

이 프로그램에서 FAIL이 발생할 수 있는 경로는 코드상 아래 7가지이며, 각각 사유가 결과 요약의 "실패 케이스" 목록에 출력됩니다.

| 유형 | 사유 메시지 | 원인 |
|---|---|---|
| 스키마 오류 | `input/expected 누락` | 케이스에 `input` 또는 `expected` 키가 없음 |
| N 추출 실패 | `키에서 N 추출 실패` | 키에 숫자 토큰이 없음 (예: `pattern_a`) |
| 필터 없음 | `필터 size_N 없음` | `filters`에 해당 크기 필터가 없음 |
| 라벨 정규화 실패(필터) | `필터 라벨(Cross/X) 정규화 실패` | 필터 키가 `cross`/`x` 계열이 아님 |
| 라벨 정규화 실패(expected) | `expected 라벨 정규화 실패` | `expected`가 `+`/`x` 계열이 아님 |
| 크기 불일치 | `크기 불일치: pattern=.., filter=..` | 패턴 크기와 필터 크기가 다름 |
| 판정 불일치 | `판정(X) != expected(Cross)` | 점수 비교 결과가 기대값과 다르거나 `UNDECIDED` |

**(a) 실패가 있는 경우** — 위 표에서 사유를 확인해 분류합니다. 특히 다음 두 가지를 구분해서 봐야 합니다.
- *데이터/표기 문제*(스키마 누락, 라벨 표기, 크기 불일치): 코드 로직이 아니라 입력 데이터 또는 정규화 규칙의 문제입니다. 라벨 표기는 `normalize_label`에 별칭을 추가하면 해결됩니다.
- *판정 불일치*: 노이즈가 섞인 패턴이어서 실제로 반대 필터 점수가 더 높게 나오는 경우입니다. 이는 MAC 방식 자체의 한계(위치 일치도만 비교)이므로, 해당 케이스의 Cross/X 점수를 직접 비교해 분석합니다. 두 점수가 거의 같다면 `UNDECIDED`로 떨어진 것입니다.

**(b) 실패가 0개인 경우 — 왜 0 FAIL이 되었는가**
1. **라벨 정규화**: `expected`는 `"+"`/`"x"`, 필터 키는 `"cross"`/`"x"`로 표기가 서로 달랐습니다. 정규화 없이 문자열을 그대로 비교하면 `"+" != "Cross"`가 되어 **정답인데도 전부 FAIL**이 됩니다. 두 쪽을 모두 `Cross`/`X`로 통일했기 때문에 이런 거짓 실패가 사라졌습니다.
2. **epsilon 정책**: 점수를 `==`가 아닌 `1e-9` 허용오차로 비교하여, 부동소수점 오차가 동점을 가짜 승패로 바꾸는 일을 막았습니다. 진짜 동점은 `UNDECIDED`로 명시해 임의로 한쪽에 몰아주지 않습니다.
3. **크기별 필터 매칭**: 키에서 N을 추출해 같은 크기의 필터(`size_N`)만 적용하므로 크기 불일치가 발생하지 않습니다.
4. **케이스 단위 예외 처리**: 오류가 나도 해당 케이스만 FAIL로 기록하고 나머지를 계속 처리하므로, 결과 집계가 항상 끝까지 완료됩니다.

### 3-3. 성능 표 해석 및 시간 복잡도 분석

**성능 분석표 (실행 후 `avg_ms` 칸을 기입)**

| 크기 (N×N) | 평균 시간 (ms, 10회 평균) | 연산 횟수 (N²) | 3×3 대비 연산 횟수 배율 | 3×3 대비 실측 배율 |
|---|---|---|---|---|
| 3×3   | `___` | 9   | 1배     | 1배 |
| 5×5   | `___` | 25  | 약 2.8배  | `___` |
| 13×13 | `___` | 169 | 약 18.8배 | `___` |
| 25×25 | `___` | 625 | 약 69.4배 | `___` |

**시간 복잡도 분석**
1. `mac()`은 행 `r`(N번) 안에서 열 `c`(N번)를 도는 **이중 반복문**이며, 안쪽에서 곱셈 1회와 덧셈 1회를 수행합니다. 따라서 `mac()` 1회의 곱셈·덧셈 횟수는 정확히 **N × N = N²** 입니다.
2. 반복문 안의 `get()` 호출, 곱셈, 덧셈은 모두 O(1)이므로 `mac()` 1회의 시간 복잡도는 **O(N²)** 입니다.
3. 입력 크기 N이 두 배가 되면 연산 횟수는 네 배가 됩니다. 표의 연산 횟수 열(9 → 25 → 169 → 625)이 이 증가를 그대로 보여 줍니다.
4. 실측 시간도 N이 커질수록 **연산 횟수에 비례해 증가**하는 경향이 나타나야 합니다. 즉 `평균 시간 ÷ N²` 값(연산 1회당 시간)이 크기와 상관없이 비슷한 수준이면 O(N²)를 뒷받침합니다.
5. 3×3처럼 매우 작은 크기에서는 연산 자체보다 함수 호출·반복문 시작 같은 **고정 오버헤드** 비중이 커서, 실측 배율이 이론 배율(2.8배 등)보다 작게 나올 수 있습니다. 반대로 25×25처럼 커지면 고정 오버헤드가 묻혀서 이론 배율에 가까워집니다.
6. 측정은 `measure_mac()`이 MAC 연산 구간만 10회 반복해 평균을 내므로, 입출력·JSON 파싱 시간은 제외됩니다. 반복 평균으로 1회 측정의 흔들림(스케줄링, 캐시 상태)도 줄입니다.
7. 모드 2에서 케이스 하나를 판정할 때는 Cross, X 두 필터로 `mac()`을 **2번** 호출하므로 비용은 2·N² 이며, 상수 2는 빅오에서 무시되어 여전히 **O(N²)** 입니다.
8. 전체 케이스 수를 K라 하면 일괄 판정의 총 시간 복잡도는 **O(K · N²)** 입니다. (크기가 섞여 있으면 케이스마다 N²을 합산)
9. 성능 표 측정에서는 크기별로 `Matrix` 생성(O(N²))이 있지만 측정 구간 밖에서 이루어지므로 평균 시간에는 포함되지 않습니다.
10. 정리하면, 이 구현은 모든 칸을 한 번씩 곱해야 하는 연산의 특성상 **N²보다 빠르게 만들 수 없고(필요한 최소 연산량과 동일)**, 필터가 커질수록 시간이 제곱으로 증가한다는 점이 성능 표의 핵심 해석입니다.
